# Reconcile missing payment callbacks with trustless receipt proofs

NEAR native transfers and their callbacks execute as separate receipts, so a callback timeout cannot prove that a transfer failed; retrying an unknown transfer risks paying twice, while waiting forever can strand a payment liability. Accepted by the user during the grill-with-docs interview on 14 November 2026 (Asia/Calcutta): Reckon will keep the callback as the fast path and add permissionless, genesis-anchored verification of finalized headers, validator-set changes, and proofs linking the exact payment attempt to its transfer action and outcome. A verified success marks the liability paid; a verified failure makes that same liability retryable. The local service relays proofs automatically, any caller may submit one, and the first implementation targets the local sandbox; testnet support is deferred.

Initialization fixes the generated sandbox genesis and its validator commitment as deployment configuration, and the verifier exposes that genesis hash for independent comparison with block zero. Proof relayers cannot replace it. Authenticated source logs record the payment terms and every promise effect in creation order. The verifier uses that order to select the exact native-transfer child, including when several calls share a source receipt. This relies on the deployed scheduler code and protocol-88 runtime ordering; the standard outcome proof does not contain a raw transfer action body. The service journals the exact signed transaction before broadcast and later its public receipt IDs, so a restarted relay can recover even if it never observed the original response. The local node runs in archive mode to retain the history needed for genesis-anchored verification. A bounded cache of 64 verified headers lets prepared proofs tolerate concurrent updates.

The five-minute callback timeout uses the contract's block timestamp at the start of the payment attempt as its authoritative clock. It only tells the keeper when to start receipt reconciliation. The keeper reads an optimistic block timestamp to schedule that work, so it may act slightly early or late relative to a finalized block. The contract does not depend on that read: it accepts a valid finalized proof at any time, and the timeout never authorizes a second payment attempt. Only a proven failure does. The relay can reconcile only attempts whose transactions it submitted or recovered from its journal. An attempt started by another caller needs a proof relayer to call `reconcile_payment` directly.
